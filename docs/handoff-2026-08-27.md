## Session 1 — Backend migration (committed, pushed, deployed)

The original app was built for folk.com's hosted platform: a proprietary
SQLite transport (`__folkdata/query`) with **no authentication at all** — its
own source comment said "no API keys, no CORS." That's fine on folk's
platform, not fine on a public Vercel URL.

What changed:

- **`api/_db.js`**: translates the small, fully-enumerated set of SQLite-only
  SQL this app uses (`AUTOINCREMENT`, `PRAGMA table_info`, `INSERT OR
  IGNORE/REPLACE`, `COLLATE NOCASE`, `date(created_at)`, bare `WHERE 0/1`,
  `CURRENT_TIMESTAMP`/`CURRENT_DATE` cast issues) into real Postgres, running
  each batch in one transaction. **The app's own source (`schema.js`,
  `data.js`) is untouched** — the translation lives entirely in the transport
  layer, so future upstream drops of the app don't need re-porting.
- **`api/query.js` + `api/_auth.js`**: replacement for `__folkdata/query`,
  gated behind a Supabase Auth session on every request. This is the real
  security fix — the admin app is genuinely private now.
- **`src/components/AuthGate.jsx`**: login screen, mounted above
  `StoreProvider` so no ledger query fires before authentication.
- **`src/lib/folkdb.js`**: same `query()`/`batch()` contract the rest of the
  app already used, now posting to `/api/query` with a bearer token instead
  of `__folkdata/query`.
- **`server/dev-api.mjs`**: local stand-in for Vercel's serverless runtime —
  `npm run dev` runs this alongside Vite so local dev talks to the real
  Supabase database without needing `vercel dev` (which needs a full project
  link and has a known hang risk on this machine per project memory).
- **`api/_db.test.js`**: unit tests for every dialect-translation rule.
- **`src/lib/calc.js`** got its first-ever test coverage
  (`src/lib/calc.test.js`) — this is the file every peso figure in the app
  comes from (deposit math, freight allocation, landed cost, profit). All
  documented formulas from the original handoff PDF were verified against
  the actual code.

**Env vars** (set in Vercel dashboard *and* in `.env.local` for local dev —
see `.env.example` for the exact shape):
- `DATABASE_URL` — Supabase **Transaction pooler** connection string (port
  6543, not the direct 5432 connection). Contains a real password; never put
  this in chat.
- `SUPABASE_URL` / `SUPABASE_ANON_KEY` — server-side, used to verify bearer
  tokens.
- `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` — same two values, client-
  side. **Must be Vercel "Config" type, not "Sensitive"** — Sensitive-type
  vars aren't exposed to the Vite build step, only to server runtime. Getting
  this wrong is exactly what caused the "Supabase isn't configured yet" error
  earlier in this session, even after multiple redeploys — the fix was
  removing and re-adding those two as Config type.

**Known deploy gotchas hit this session** (all fixed, documented here so they
don't cost another hour if they resurface): Vercel's own Supabase integration
auto-injects a large bundle of `POSTGRES_*` / `NEXT_PUBLIC_SUPABASE_*` /
`SUPABASE_SERVICE_ROLE_KEY` vars into this project — harmless, just noise,
don't confuse them with the four vars this app actually reads.

## Session 2 — Storefront redesign (uncommitted as of this doc)

**Trigger**: current design looked "too AI-made"; asked to redesign using
[pickleclubdavao.com](https://pickleclubdavao.com) as a UI/UX reference
(browsed live via Claude in Chrome — no purchase was completed there, just
observed the design and checkout flow structure).

**Decisions made** (via AskUserQuestion, don't re-litigate without reason):
- Keep PTG's existing forest-green/teal palette — do **not** adopt the
  reference site's pastel pink/olive look.
- Full redesign: real per-product detail pages + a polished checkout, **no**
  product-compare feature (not worth it for a ~16-item paddle catalog).

**What changed in `src/pages/PublicCatalog.jsx`**:
- Added client-side routing (`react-router-dom`, `basename={PUBLIC_CATALOG_PATH}`)
  so paddles now have real linkable pages at
  `/public/paddles-7x4k/paddle/:id` — breadcrumb, large image, colour/variant
  picker, quantity stepper, and an honest "Details" card (brand/category/SKU/
  deposit) built only from real data, no fabricated specs.
- `src/App.jsx`'s `isPublicCatalog()` check changed from exact-match to
  prefix-match so nested storefront routes still count as the public route
  (and correctly stay outside admin auth).
- Checkout rewritten into numbered step cards (1 Contact → 2 Fulfilment → 3
  Payment Summary → 4 Scan to Pay → 5 Proof of Payment), visually matching
  the reference site's clarity. All existing validation/business logic
  (50% deposit, non-refundable acknowledgment, receipt compression) is
  unchanged — this was a visual/structural pass, not a logic rewrite.
- New CSS in `src/public.css`: breadcrumb, product-page grid layout, numbered
  step badges — all using the existing `--forest`/`--teal` tokens.

**A real, separate bug this surfaced and fixed**: the redesigned storefront
initially couldn't load *any* products, because `PublicCatalog.jsx` shared the
same `/api/query` transport as the admin app — which Session 1 had (correctly)
locked behind Supabase login. Anonymous shoppers got 401'd. Fixed by actually
mounting the pre-existing (never-wired) `api/v1/catalog.js` /
`api/v1/orders.js` reference implementation from the original folk handoff:

- **`api/v1/_node-adapter.js`** (new): bridges Vercel's Node `(req, res)`
  convention to the Fetch-standard `(Request) => Response` signature those
  handlers were written against.
- **`api/_db.js`**: added `webDbAdapter()` export giving those handlers the
  `db.query()`/`db.batch()` shape they expect.
- **`api/v1/catalog.js` / `orders.js`**: added `export default` entry points.
  Deliberately **skip `requireApiKey`** — this storefront and this API share
  one origin, so a bearer key would have to be baked into the public client
  bundle anyway, gating nothing a browser devtools Network tab couldn't
  defeat. Rate limiting is the real abuse guard; `createOrder()`'s own
  re-validation (live prices, live availability, bounded fields, INSERT-only)
  is the real write boundary.
- **`api/v1/_shared.js`**: fixed three latent bugs found while wiring this up
  for the first time (it was never actually run before):
  1. `createOrder`'s SQL checked `inventory.active`, a column that doesn't
     exist in this schema (archived products use a `[archived]` notes
     marker instead) — would have thrown on every real order.
  2. Payment proof was being buried inside a JSON blob in `notes` instead of
     the real `payment_proof_url` column the admin's order view actually
     reads — "view payment proof" would have shown nothing.
  3. Customer address was required unconditionally, even for pickup orders,
     contradicting the app's own pickup-arranges-later design.
  4. `MAX_BODY_BYTES` (32KB) was too small for the base64 receipt images this
     app actually sends (up to 150,000 chars) — raised to 200KB.
- **`api/_db.js`**: dialect translator gained two more rules found via this
  wiring: `CURRENT_DATE` needed the same TEXT-column cast as
  `CURRENT_TIMESTAMP`, and `COLLATE NOCASE` on an **alias-qualified** column
  (`i.name COLLATE NOCASE`, used in the v1 API's joined queries) was
  producing invalid SQL (`i.LOWER(name)`) — the regex now handles both bare
  and qualified columns. Both have new tests in `api/_db.test.js`.
- **`server/dev-api.mjs`**: now routes `/api/v1/catalog` and `/api/v1/orders`
  locally too, not just `/api/query`.

**Verified working end to end this session** (then cleaned up — no test data
left behind):
- Anonymous catalog load via `/api/v1/catalog` (16 products returned).
- Product detail page navigation, colour picker, "Sold out" vs "Available
  now" states.
- Add to cart → cart panel → numbered checkout UI.
- Order creation via direct API call to `/api/v1/orders` (couldn't drive the
  file-upload step through browser automation — no OS file picker access —
  so verified this leg via a direct `curl` POST instead): correct pricing,
  correct 50% deposit, real `payment_proof_url` column populated, real order
  number, order_items row correct.

## Local dev quick start

```bash
cd ~/Projects/ptg-admin-hub
npm install               # if node_modules isn't already there
npm run dev                # runs Vite + server/dev-api.mjs together
```

Needs `.env.local` filled in (copy `.env.example`, see Session 1's env var
notes above). Admin login: `ptg@ptg-admin.local` — password known to the
user, not recorded here.

To poke the database directly for maintenance/testing (bypasses admin login
entirely, uses the same `DATABASE_URL`):

```bash
node --env-file=.env.local -e "
import('./api/_db.js').then(async ({ runStatements }) => {
  const [result] = await runStatements([{ sql: 'SELECT 1' }]);
  console.log(result);
  process.exit(0);
});
"
```

## Things to never re-do

- Don't reintroduce an unauthenticated `/api/query`-style endpoint — that was
  the whole point of Session 1.
- Don't put `DATABASE_URL` or any password in chat, ever, even in a "just the
  shape of it" way. If a connection string needs debugging, check its
  structure via a script that never prints the actual credential (see the
  pattern used throughout Session 1 — checking for stray `<>` brackets,
  wrong ports, etc. without ever displaying the value).
- Don't hand-edit SQLite-dialect quirks into `schema.js`/`data.js` — the
  translation layer in `api/_db.js` is the only place dialect fixes belong,
  specifically so future folk-source drops don't need re-porting.
